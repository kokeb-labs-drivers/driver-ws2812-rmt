Recurring defects¶

The defects that reached an independent reviewer or the first CI run of more than one driver, one entry per class. Review skills cite these ids; the mechanization policy says where each class is caught and when it moves up a level. Append new findings to the entry they belong to, or add an entry (see the policy).

Evidence names the driver, the review round (reviews/<driver>-review<N>.md, finding id) or the CI run (reports/<driver>-ci-*.txt). Code examples are generic and minimal; none quotes a datasheet or a standard.

Detection levels: lint (a script in the preflight or the gate, no judgement), test (a model knob, a mutation, a fuzz property or a compile-fail case that fails when the defect is present), review (a named reviewer asks one question). Status: enforced is in the template now; planned is the target, tracked in the policy's backlog, and until it lands the level below it (test, then review) is what protects the driver.

Chip-protocol and safety classes¶

RD-01 Write after an unseen device reset¶

Rule: every way the chip can reset itself is detected from evidence the chip leaves, and no cached value is written over a chip that may have reset.

// bad: the chip browned out; shadow_ holds the old setpoint, the chip is at its reset value
// bad: writes the whole shadow_ (the stale rest of it) over a chip that may have reset
Result<void> SetLimit(uint8_t v) { shadow_.limit = v; return WriteReg(kLimit, Pack(shadow_)); }
// good: check the evidence first, refuse until the application re-initialises
Result<void> SetLimit(uint8_t v) {
  if (auto r = ResetCheck(); !r) { return r; }        // status read, sentinel compare; pending until it passes
  return WriteReg(kLimit, Pack(WithLimit(shadow_, v)));
}

Hurts: stale state rewritten into a chip at reset values energises outputs or sets limits the application never chose; the call returns Ok. Seen: ads9324 (review1 J1), pf1550 (review1 M8, review2 F1, review3 N1, review4 R4-1, review5 R5-2), tmc5160 (review1 M5), fdo2 (review1 B1: abort during start-up leaves the driver initialised). 4 drivers. Detection: test: model knob "reset mid-session" (registers to reset values, reset flags set) plus a fuzz property "no write after a reset is seen"; mutate the sentinel compare and the pending-check latch, each must fail a test. review: hardware-lessons-review 12a. Question: "List every way this chip resets or reloads; for each, which bit or sentinel shows it, which function reads it, and what does a setter do between the reset and that read?"

RD-02 Decision from one unvalidated read¶

Rule: a read that decides a write, a state change or an identity is validated per the protocol (CRC, echo, length) and a read-modify-write uses only a validated read; a single bad read never clears state or masks a lost write.

// bad: one flipped read clears identity, the next switch-off returns NotInitialized and sends nothing
if (ReadReg(kId) != kExpectedId) { identified_ = false; }
// good: two agreeing reads before a state is dropped; switch-off ignores identified_

Hurts: a transient line error becomes "device reset" or "not initialised", a read-modify-write writes garbage bits back, a resync hides a lost write so the chip runs at the wrong current. Seen: pf1550 (review1 B1, M1; review4 R4-3), ads9324 (review1 J2), tmc5160 (review1 M1, lost-write masking by resync), sfm (review1 B1: any NACK after a first sample became DeviceReset), fdo2 (review1 B1). 5 drivers. Detection: test: model fault "one flipped reply at call k" swept over every call of every public function; the expected result is the call's own error, no state loss, no unsafe write. review: hardware-lessons-review 1, 12. Question: "Which reads in this driver decide something, and is there a mutant that removes each validation?"

RD-03 Stuck or floating line accepted as data¶

Rule: a reply a dead, shorted or floating line can produce (all zeros, all ones, the command echoed, one word repeated) is never a measurement or a ready status.

// bad: an all-zero frame has a valid CRC for init 0x00, so 0 degC (or -200 degC after the offset) is returned
auto t = DecodeTemperature(words);
// good: reject by pattern before decoding, then plausibility-check the decoded value
if (IsStuck(words)) { return Error::NoDevice; }

Hurts: a wrong value is returned as data, which downstream control trusts. Seen: ads9324 (review1 J3), tmc5160 (review1 M8), sfm (review3 M-A: the temperature path had no stuck check while the sample path had one). 3 drivers. Detection: test: one model fault per pattern (zeros, ones, echo, repeat) applied to every read function; a table test lists each public read function and the fault, so a new read function without a row fails. review: hardware-lessons-review 4. Question: "For each read path, which of the four patterns does the CRC pass, and which line in the code refuses it?"

RD-04 Invalid argument still sends something¶

Rule: a call that returns InvalidArgument (or any precondition error) sent nothing and changed nothing; validate first, transfer second.

// bad: reads the position first, then rejects the argument
auto pos = ReadPos(); if (steps > kMax) { return Error::InvalidArgument; }
// good
if (steps > kMax) { return Error::InvalidArgument; }
auto pos = ReadPos();

Hurts: a rejected call moves state or leaves the driver config invalid, and the next call sends from it. Seen: tmc5160 (review1 M2: three sites, found by a fuzz abort), ads9324 (review2 N2: a division by convst_hz before the state check). 2 drivers. Detection: test: the model counts frames; every InvalidArgument test asserts the count is unchanged, and the fuzz target asserts it for every call that returned InvalidArgument. review: hardware-lessons-review 11. Question: "For each early return of an argument error, what is the first line above it that touches the port?"

RD-05 Stop, switch-off or release refused¶

Rule: a switch-off, a release to input and Deinitialize() are never refused for any uncertainty (reset report, failed read, unknown mode, uninitialised after reset) and always send their writes, in the smallest atomic form.

// bad
Result<void> Off() { if (!identified_) { return Error::NotInitialized; } return Write(kEnable, 0); }
// good: acts first, reports after
Result<void> Off() { auto r = Write(kEnable, 0); MarkUnverified(); return r; }

Hurts: the one command that makes the system safe is the one that fails when the system is most in doubt. Seen: ads9324 (review2 N1), pf1550 (review2 F2, review3 N2, review4 R4-3), tmc5160 (review3: stop and switch-off refused after a reset report; review1 M4: not verified on UART), alicat (review2 N3: a switch-off in an unknown state is sent only to the held settings). 4 drivers. Detection: test: for every uncertainty flag the driver has, a test sets it through the model and asserts the switch-off still writes (mutation: add the refusal back, the test fails). review: hardware-lessons-review 12c. Question: "Name each flag that can make a call return early; show the test where it is set and Off still sends."

RD-06 Transfer buffers on the stack¶

Rule: buffers handed to the bus are members of the driver object (memory a DMA engine reaches), never locals or function-local statics.

// bad
Result<void> Read(Reg r) { std::array<uint8_t, 4> tx{}; return port_.Transfer(tx.data(), rx, 4); }
// good
std::array<uint8_t, 4> tx_{};   // member

Hurts: DMA or TCM-stack ports fail on the first frame; the host build and a DMA-disabled example hide it. Seen: ads9324 (review2 N3), pf1550 (review3 N3), bno08x (review1 M-1, UART receive buffers, and the contract said the opposite), tmc5160 (review3 M3; its fix was killed by an address-in-object test, review4). 4 drivers. Alicat keeps its buffers in the bus object (review3). The ads9324 fix still had a survivor that pinned no ownership (review3 m2): the address test below closes that. Detection: test: the mock port records the address of every transmit and receive buffer and asserts it lies inside [&driver, &driver + sizeof(driver)); compile it into the shared model. review: KB-HW-019. Question: "In every function that calls the port, where does the memory of each buffer argument live?"

RD-07 Chip model shares the driver's misreading¶

Rule: the model is written from the datasheet, including frame layout, not from the driver; golden frames are transcribed from the datasheet's figures and checked by a test the driver's author did not derive from the code.

// bad: driver and model both put the data in bytes 1..2 of the reply, the datasheet says bytes 0..1 of the data word
// good: test_model.cpp pins a golden frame copied from the datasheet figure; model includes no driver header

Hurts: green tests, wrong data on the wire; only hardware or an independent reader shows it. Seen: ads9324 (review1 B1: wrong bits of the reply, model and driver agreed), tmc5160 (review5 m2: the model set a status bit the instant the velocity was zero, the chip sets it 2^20 clocks later). 2 drivers. Detection: lint: tests/mock_*.hpp includes no driver header (planned, preflight model-standalone); review: datasheet-conformance, independence check. Question: "Take one golden frame from the datasheet figure; which test fails if the driver and the model both decode it the other way?"

RD-10 Incomplete state-machine guard¶

Rule: every command is checked against every state the chip or the driver can be in, including pending timers, power gates, asleep and in-doubt; a start-up that leaves anything pending does not energise.

// bad: waits only for velocity == 0, but the chip is still counting a stand-still delay and will drive back
while (Velocity() != 0) { }  Enable();
// good: also checks the pending-delay flag the datasheet names
while (Velocity() != 0 || DelayActive()) { }  Enable();

Hurts: outputs energise in a state the guard did not consider; the motion or power surprise is real. Seen: tmc5160 (review5 M1: enable during a pending zero-wait), ws2812 (review2 N1: the power gate started open), pf1550 (review1 M3, M4: rail enabled with a voltage no limit checked), sfm (review1 M2: soft reset accepted while asleep), fdo2 (review1 B1). 5 drivers. Detection: test: a generated state x command table test (every public command in every modelled state, expected result and frame count), and a mutant for each guard. review: hardware-lessons-review 11, 12. Question: "Draw the states from the datasheet; for each command and state, where is the guard and which test removes it?"

RD-30 Out-of-bounds or UB before a guard¶

Rule: bounds, divisors and state are checked before they are used, on every path, including the framing layer.

Hurts: abort in hardened builds, UB elsewhere. Seen: bno08x (review1 B-1: a framer returned a frame longer than its buffer), ads9324 (review2 N2: divide before the state check), tmc5160 (review1: fuzz aborts, see RD-04). 3 drivers. Detection: test: libFuzzer with ASan and UBSan in the gate (enforced); fuzz target feeds every public function. review: question "which divisor, index or span length comes from a caller or the chip, and where is it checked?"

RD-31 Clear-on-read flags lost by a diagnostic read¶

Rule: clear-on-read and write-1-to-clear flags collect in one driver-owned latch; a self-check or raw read never discards them.

Seen: pf1550 (review1 M2: SelfCheck() and ReadRegister() read status registers the chip clears on read), tmc5160 (review1: Service() cleared the stall event, a BLOCKER, review1 B1). 2 drivers. Detection: test: model with clear-on-read bits; test reads through every diagnostic path, then asserts the latch still reports the fault. review: hardware-lessons-review 10, 12b.

Datasheet and documentation classes¶

RD-28 Datasheet misread in a decode, clear or timing¶

Rule: every field position, clear semantic, wait and gap cites its section and has a test that pins it independently.

Seen: ads9324 (review1 B1, J4), tmc5160 (review1 B1), sfm (review1 M3, M4), ws2812 (review1 M2, M3), fdo2 (review1 M3, M4). 6 drivers. Detection: review (datasheet-conformance): re-derive the five facts the change touches from the datasheet before reading the code. Question: "For this register or frame, what do the datasheet's bits say, and does the code agree before you look at the model?"

RD-29 Hardware doc exceeds a datasheet limit¶

Rule: a reference circuit, wiring table or example never exceeds an absolute maximum or ties a pin the datasheet forbids tying.

Seen: ws2812 (review1 M7), fdo2 (review1 M9), ws2812 (review1 M3: documents disagree on the input threshold). 3 drivers. Detection: review: docs and diagram pass. Question: "For each net in the reference circuit, what is the highest voltage the chip pin sees, and where does the datasheet allow it?"

RD-09 Docs promise behaviour the code lacks¶

Rule: every behavioural claim in docs, Doxygen, the contract and the build report is checked against the code line that implements it and the test that pins it.

/// Enables the bridge again.            // doc
Result<void> ClearFaults();              // code returns Busy while the motor moves and stays disabled

Hurts: callers and later reviewers rely on the claim; a promised error never occurs, a promised recovery never runs. Seen: ws2812 (review1 M5, review2 N2, n9), tmc5160 (review1 M4, review5 m1), fdo2 (review1 M7), pf1550 (review1 M6), bno08x (review1 M-1), ads9324 (review1 J5-J7). 6 drivers. Detection: review via the review-round claims-vs-code check: list every "always", "never", "returns", "enables" in docs and the build report and cite the code line and test for each. Mechanical part (lint, planned): every Error named in docs exists; every Doxygen @return lists the values the function can return.

RD-08 False coverage matrix or fuzz claim¶

Rule: a matrix row, test id or knob named in docs exists in code, and a row's test asserts the row.

Seen: ads9324 (review1 J5, J6: 873 rows unproved, fuzz claims invariants it does not check), pf1550 (review2 F4: 47 rows cite symbols that do not exist; F5: knobs that do not exist; review1 M11), ws2812 (review2 n9: "each fix has a test" overstated). 3 drivers. Detection: lint (planned claims-symbols): every backticked identifier in the datasheet coverage page, the coverage matrix and docs/ambiguities.md resolves with grep in inc/ src/ tests/. review: row-level sample.

RD-32 Docs style¶

Rule: Markdown lines are at most 120 characters, list items are separated, text changed by a fix is updated everywhere.

Seen: ws2812 (review2 n4, n5, n6), ntc (review1), mcp9700 (review2 m2-1). 3 drivers. Detection: lint (enforced: markdownlint in the preflight; line length 120). Stale text after a change is RD-09.

RD-33 Another project's name or dated history¶

Seen: ntc (review1 M5: old-history wording in eleven places). 1 driver; enforced by tools/check_standalone.py.

Process and test-quality classes¶

RD-25 Guards no test kills¶

Rule: every guard that protects a write, a state or a value has a test that fails when the guard is removed.

Seen: ads9324 (review1 mutants M22 to N66), pf1550 (review2 F3, review3 N4, review4 R4-2: 7 of 12 survivors matter, review5 R5-1), tmc5160 (review1 M6: 22 of 50 survive), bno08x (review1 M-3: 33 survive), alicat (review2, review3). 6 drivers. Detection: test: a mutation runner over the guard lines (one-edit mutants: negate, drop, swap constant), built by the reviewer in each round; target: a template tools/mutate.py run by the gate with a survivor budget of zero on guards. review: the review-round mutant check of fixes.

RD-26 Fuzz target does not check the safety rules¶

Rule: the fuzz target asserts the invariants of the safety rules (no write after a reset is seen, no switch-on in doubt, no frame after InvalidArgument), and a mutant of each invariant fails it.

Seen: ads9324 (review1 J6), pf1550 (review1 M10, review3 N4: blind to a missed reset), alicat (review2 m9, review3 m9: no no-write-in-doubt invariant). 3 drivers. Detection: test: mutate the invariant check in the harness; review: question "which safety rule does the fuzz target assert, and what input would break each?"

RD-34 Unspecified evaluation order in a test check¶

Rule: a call in a test or fuzz target takes, as separate arguments, no operation that changes state together with a read of that state (sent(), Transfers(), pending(), a flag, a counter, a clock). The order of the arguments of a call, of the operands of + - == < and of the two sides of an assignment is unspecified; GCC on x86-64 evaluates arguments right to left, Clang and GCC on aarch64 left to right. Braced-init lists, &&, ||, ?: and , are sequenced. Two reads of the fuzzer's input (in.Byte(), FuzzConfig(in)) in one expression count as well: they advance the input, so the same corpus file decodes into different calls per compiler.

// bad: x86-64 GCC reads sent() before the call, so it is always 0 here
Check(d.Write(v), was_up, sent());
// good: the result first, then the read; or pass the probe and read it inside the helper, after the call
const auto r = d.Write(v);
Check(r, was_up, sent());

Hurts: the check passes, or aborts, on one CI runner only. A "nothing was sent" promise becomes vacuous, and a positive promise (sent >= 1) aborts on a correct driver; neither shows on an Apple-silicon or aarch64 rehearsal. Seen: dynamixel (first CI, sent >= 1 aborted on x86-64 GCC only), pcal9555 (three fuzz cases, latent), tle92466ed (16 fuzz cases, vacuous; 6 more with two input reads), the template's own fuzz target (5 cases). 3 drivers, all copies of the same pattern. Detection: lint (enforced): tools/eval_order_check.py, the eval-order preflight step, scans tests/ and examples/. test: the fuzz replay with a one-edit mutant that must abort (mutant_replay_*, kept out of the fuzz_* names so the libFuzzer job does not pick it up).

RD-24 Missing gitlink for the scripts submodule¶

Seen: sfm (review3 M-B), mcp9700 first push (the ESP32 examples job fails: no such directory). 2 drivers. Detection: lint (enforced): the gate runs git ls-files -s | grep ^160000 after setting the pinned commit.

RD-19 Template drift¶

Seen: fdo2 (reports/fdo2-ci2.txt: drift warning and a 160-character workflow line), alicat (review1 m6) and pf1550 (review4 m-3): the template record said unknown. 3 drivers. Detection: lint (enforced): scaffold.py --check-drift in the gate.

RD-27 Local tidy and format differ from CI¶

Rule: the preflight runs clang-format 20 and clang-tidy over the same file list and compile database as CI, inside the container.

Seen: ntc (first CI: tidy failed on a generated file absent from a configure-only database), bno08x (review1 M-2: readability-named-parameter in the install consumer), fdo2 (reports/fdo2-ci-failed.log: lint job, 2 files), fdo2 later (tidy on the ESP32 stub). 4 drivers. Detection: lint (enforced in the container preflight once it uses a configure-only database; check the log names the tidy file count).

CI-only checks (MISRA scan, ESP-IDF, compile-fail)¶

RD-11 Header outside the library subset¶

Rule: #include <...> in inc/ and src/ is only from the driver subset of the handbook (KB-CPP-012).

#include <numeric>   // bad: not in the subset; std::accumulate -> write the OR out
#include <string_view>

Seen: fdo2 (reports/fdo2-ci2.txt, <string_view>), tmc5160 (review4 B1, <numeric>). 2 drivers; the second hit makes it a lint. Detection: lint (enforced in handbook_check; the preflight must also run the include scan or grep).

RD-12 Rule 7.0.3 character arithmetic¶

Rule: no arithmetic or comparison on a char value, including c - '0' and c == 'x'.

int d = c - '0';                 // bad
if (c == 'A') {}                 // bad
const int d = DigitValue(c);     // good: lookup in a constexpr digit array via std::find

Seen: fdo2 (reports/fdo2-ci-misra.txt, reports/fdo2-ci2.txt: the bare comparisons too), alicat (review2: about 30 computations predicted; review3 R3-M1, six conversions; m-10, tests), pf1550 (review4 m-4: a template file used in tests). 3 drivers. Detection: lint: misra_lint rule 7.0.3 (planned): char literals in arithmetic or comparison in inc src tests examples. Until then: grep '.' next to -, +, ==, !=.

RD-13 Rule 8.0.1 missing parentheses¶

Rule: a binary operand that is itself a binary expression of higher precedence is parenthesised, in static_assert too.

static_assert(kA == 1 && kB < 2);           // bad
static_assert((kA == 1) && (kB < 2));       // good

Seen: ads9324 (reports/ads9324-ci-misra.txt, three lines), pf1550 (review4 m-1: static_asserts). 2 drivers. Detection: lint: misra_lint rule 8.0.1 (planned): parenthesis-depth scan of inc src tests.

RD-14 Rule 9.4.1 else-less chain¶

Rule: every if ... else if chain ends with else, with a comment when empty; in tests and models too.

Seen: ads9324 (reports/ads9324-ci-misra.txt), fdo2 (reports/fdo2-ci3.txt), tmc5160 (review5 B1: two chains in the model). 3 drivers. Detection: lint: misra_lint rule 9.4.1 (planned).

RD-15 Rule 0.1.2 unused return value¶

Seen: fdo2 (reports/fdo2-ci-misra.txt: failInit). 1 driver. Detection: lint: rule 0.1.2 (planned): a call to a non-void function as an expression statement; mark with an explicit discard where intended.

RD-16 Rule 13.3.3 parameter names differ¶

Seen: fdo2 (reports/fdo2-ci-misra.txt: checkOxygen). 1 driver. Detection: lint: rule 13.3.3 (planned): declaration in inc/ against definition in src/*.ipp.

RD-17 Rule 7.0.6 literal argument type¶

Rule: a constant argument has its parameter's type (_u32 literal), and no mixed-width arithmetic on literals.

Seen: ntc (review1 M3), fdo2 (review1 M10), tmc5160 (review1 M7), ws2812 (review1: call sites). 4 drivers. Detection: lint (partial, planned): literal passed to a uint32_t or uint8_t parameter of a known function; review for the rest (the CI scan is final). Question: "Which call passes a bare integer constant to a narrower parameter?"

RD-18 Advisories 6.9.2, 15.1.4, 0.0.2¶

Rule: these three appear on every driver and need no re-report: 6.9.2 on the unsigned long long literal-operator parameter and on the version getters, 15.1.4 on a constructor whose members have default initialisers, 0.0.2 on a condition a constant-hook port makes always the same. Seen in CI: fdo2, ads9324 (reports/fdo2-ci-misra.txt, reports/ads9324-ci-misra.txt); predicted by the reviewer from those runs: pf1550 (review3, review4 m-4), alicat (review3, review4), bno08x (review1). 5 drivers. Detection: lint (planned): the gate compares the CodeQL advisory list to this known list; anything else is new. Reviewers do not report the known three; whether to record them as deviations is an owner decision.

RD-20 ESP-IDF REQUIRES incomplete¶

Rule: every #include of an ESP-IDF header in examples/esp32/main has its component in REQUIRES.

Seen: fdo2 (reports/fdo2-ci-failed.log: esp_timer.h; the ESP32 job failed in both examples). Later reviews found it clean (pf1550 review5). 1 driver. Detection: lint (planned): include-to-component map checked against the idf_component_register call.

RD-21 ESP32 example cannot start with its defaults¶

Rule: the example's default pins and Config start up; an optional hook returns true when the pin is absent.

Seen: fdo2 (review1 M5), mcp9700 (review1 B-1: GpioSet returned false with the default -1 pin), ntc (review1 M1). 3 drivers. Detection: test: build the ESP32 port against stub ESP headers on the host and run the example's start-up with default Config. review: question "does app_main with the default pins reach the first measurement?"

RD-22 Compile-fail regex wording differs by compiler¶

Rule: an EXPECT: is a concept or type name, or the static_assert text, never compiler wording.

Seen: no CI failure yet. Reviewers could not confirm GCC 13/14 and clang CI wording for alicat, pf1550, bno08x (review4, review5, review1). 0 driver hits; listed because it is unverified each time. Detection: lint (planned): every EXPECT: string is static assertion failed, an identifier, or a string from a static_assert.

RD-23 Tests are also scanned by MISRA¶

Rule: the MISRA job builds with tests on, so tests/, models, fuzz and consumers meet the same rules as inc/.

Seen: tmc5160 (review5 B1, the model), alicat (review3 m-10: char compares in tests and the model, "if CodeQL scans tests"). 2 drivers; whether the job reports test files is not proved by the two CI runs on file. Detection: lint: every misra_lint rule scans tests/ examples/ as well as inc/ src/.
